# 浏览器扩展（Edge / Chrome）导入可行性分析

> 结论先行：**完整导入商店里的扩展不可行，是 Electron 的明确非目标**。
> 但有一小部分扩展（内容脚本类）可以通过转换导入，且与现有的油猴导入机制同源。
>
> 本文基于 Electron 31.7.7 与本项目当前架构（webview 多标签 + `defaultSession`）分析。

---

## 一、决定性事实：Electron 官方立场

来自 [Electron 官方文档 · Chrome Extension Support](https://www.electronjs.org/docs/latest/api/extensions)（原文要点）：

> Electron supports a subset of the Chrome Extensions API, primarily to support DevTools extensions and Chromium-internal extensions.
>
> **Electron does not support arbitrary Chrome extensions from the store, and it is a non-goal of the Electron project to be perfectly compatible with Chrome's implementation of Extensions.**
>
> Electron only supports loading **unpacked** extensions (i.e., `.crx` files do **not** work).
>
> Loaded extensions will **not be automatically remembered** across exits.
>
> Loading extensions is only supported in **persistent sessions**.

这四句话直接决定了可行性的天花板：

| 限制 | 后果 |
|---|---|
| 不支持任意商店扩展，且是**非目标** | 不要期待"装上就能用" |
| 只支持**未打包**（解压后的目录） | `.crx` 必须先解压；商店一键安装走不通 |
| 重启不记忆 | 每次启动都要重新 `loadExtension` |
| 仅持久化 session | 内存 session 会抛错 |

## 二、Electron 实际支持的 API 范围

官方列的**全部**支持项（没有列的就是"临时支持，可能随时移除"）：

| API | 支持程度 |
|---|---|
| `chrome.devtools.*` | 完整（`inspectedWindow` / `network` / `panels`） |
| `chrome.scripting` | **完整** |
| `chrome.webRequest` | 完整（但 Electron 自身的 `webRequest` 优先级更高） |
| `chrome.runtime` | 部分（`sendMessage` / `connect` / `getURL` / `onMessage` 等） |
| `chrome.tabs` | **部分**（`query` 只支持 url/title/audible/active/muted；`-1` 语义不支持） |
| `chrome.storage` | **只有 `local`**，`sync`/`managed` 不支持 |
| `chrome.management` / `chrome.extension` | 少量方法 |

**明确不支持**（对摸鱼类扩展影响很大）：

- `chrome.declarativeNetRequest` —— Manifest V3 的**主流广告拦截方式**，不支持
- `chrome.storage.sync` / `managed`
- `chrome.contextMenus`（右键菜单）
- `chrome.action` / `chrome.browserAction`（工具栏图标按钮）
- `chrome.notifications`、`chrome.alarms`、`chrome.cookies`、`chrome.downloads`
- `chrome.omnibox`、`chrome.commands`

**支持的 manifest 键**也有限：`name`、`version`、`author`、`permissions`、`content_scripts`、`default_locale`、`devtools_page`、`short_name`、`host_permissions`、`manifest_version`、`background`(MV2)、`minimum_chrome_version`。

**注意 `action` / `options_page` / `web_accessible_resources` 等键未列出。**

## 三、对本项目架构的具体影响

### 3.1 webview 用 `defaultSession`，这是好消息

项目**没有给 webview 配 `partition`**，所有标签共用 `defaultSession`。而 `loadExtension` 正好要求持久化 session——所以理论上可以加载到 `defaultSession`，覆盖所有标签。

如果要加载扩展，代码大致是：

```js
// electron/main.js（app.whenReady 之后）
const extPath = path.join(app.getPath('userData'), 'extensions', '<id>')
await session.defaultSession.loadExtension(extPath, { allowFileAccess: true })
```

### 3.2 但内容脚本能否注入 webview 是最大不确定性

官方文档**没有明确说明** `content_scripts` 是否注入到 `<webview>` 的 guest 页面。社区报告不一致：有说可行的，也有说 `<webview>` 的独立 webContents 不在扩展的注入范围内。

**这一点必须在真实环境中验证**，否则整个方案是空中楼阁。验证方法见第五节。

### 3.3 与现有油猴导入的关系

值得注意：**内容脚本类扩展和油猴脚本本质是同一种东西**——都是"匹配 URL → 注入 JS/CSS"。而项目**已经实现了**油猴导入（`isUserscript` / `convertUserscriptToRule`）。

所以更现实的路径不是"支持 Chrome 扩展"，而是**扩展已有的转换器**，让它也能解析扩展目录。

## 四、三条可行路径对比

### 路径 A：直接 `loadExtension`（官方 API）

| 维度 | 评估 |
|---|---|
| 可行性 | **低**。仅支持 DevTools 类与极少数简单扩展 |
| 工作量 | 中（解压 crx、持久化目录、启动加载、UI 管理） |
| 风险 | **高**。非官方支持路径，Electron 升级可能失效；内容脚本注入 webview 存疑 |
| 覆盖场景 | 大概只有"纯 content_scripts + 不用任何 action/右键菜单"的扩展 |

### 路径 B：转换扩展为本站规则（推荐）

**思路**：读取扩展目录的 `manifest.json`，把 `content_scripts` 转换成现有的数据型规则。

```
解压的扩展目录/
  manifest.json
    ├─ content_scripts[].matches  → 规则的 pattern（复用 convertUserscriptPatterns）
    ├─ content_scripts[].css      → 规则的 customCss（读文件内容）
    └─ content_scripts[].js       → 规则的 customJs（读文件内容）
```

| 维度 | 评估 |
|---|---|
| 可行性 | **高**。复用已有规则系统与注入链路，不依赖 Electron 扩展 API |
| 工作量 | 小～中。主要是 manifest 解析 + 文件读取 |
| 风险 | 低。走的是已验证的规则注入路径 |
| 覆盖场景 | **纯内容脚本类扩展**（去广告 CSS、页面美化、字号调整等） |
| 不覆盖 | 依赖 background service worker、`chrome.*` API、右键菜单、弹窗的扩展 |

**与油猴导入的差异**：油猴脚本是单文件文本，扩展是多文件目录，需要：
1. 选目录（而非选文件）—— HTML 的 `<input webkitdirectory>` 可做到
2. 读多个文件（`content_scripts` 里可能有多个 js/css）
3. 处理 `chrome.*` API 调用——**必须给出明确的兼容性警告**，因为大概率不可用

### 路径 C：只支持 DevTools 类扩展

Electron 对 DevTools 扩展支持最完整。但对摸鱼软件没意义，**不建议**。

## 五、如果要做，必须先验证的前置问题

在写任何代码前，**先花 30 分钟验证这三件事**：

### 验证 1：内容脚本能否注入 webview

准备一个最小扩展：

```
test-ext/
  manifest.json
  content.js     ← console.log('EXT INJECTED')
```

```json
{
  "manifest_version": 3,
  "name": "test",
  "version": "1.0",
  "content_scripts": [{ "matches": ["<all_urls>"], "js": ["content.js"] }]
}
```

在 `main.js` 里 `session.defaultSession.loadExtension(testExtPath)`，然后打开一个网页，看 Console 有无输出。

- **有输出** → 路径 A 可行，可继续评估
- **无输出** → 路径 A 直接否决，只能走路径 B

### 验证 2：`.crx` 解压

商店下载的是 `.crx`（本质是带头的 zip）。需要：
- 剥掉头部（CRX3 格式有 protobuf 头）后当 zip 解压，或
- 让用户自己用工具解压后选目录（**推荐**，省事且不引入解析风险）

### 验证 3：会话隔离与清理的交互

项目已有 `clearCacheOnExit`（退出清 `defaultSession`）。若加载了扩展，`clearStorageData` 会**清掉扩展的 `chrome.storage.local` 数据**。需要决定：

- 扩展数据一并清除（符合隐私设定）
- 还是排除扩展的存储（扩展设置得以保留）

## 六、建议的实施流程（若走路径 B）

```
阶段 0（前置验证，必做）
  └─ 按第五节验证内容脚本注入与 crx 解压

阶段 1：manifest 解析器（约 1 天）
  ├─ 新增 parseExtensionManifest(json)
  ├─ 复用 convertUserscriptPatterns 处理 matches
  ├─ 新增 readExtensionFiles(dir) —— 读 content_scripts 里的 js/css 内容
  └─ 输出数据型规则（与油猴导入同一形态）

阶段 2：UI（约 0.5 天）
  ├─ RulesPage 增加「导入浏览器扩展」按钮
  ├─ <input type="file" webkitdirectory> 选目录
  └─ 展示兼容性报告（哪些 API 不支持、哪些脚本会被跳过）

阶段 3：兼容性提示（约 0.5 天）
  ├─ 静态扫描 content_scripts 内容，检测 chrome.* / browser.* 调用
  ├─ 检测是否依赖 background service worker（MV3）
  └─ 在导入结果中明确列出「此扩展可能不完整」
```

**与油猴导入复用程度**：`convertUserscriptPatterns` 可直接用于 `matches`（格式同为 `*://*.example.com/*`），其余是新代码。

## 七、结论与建议

| 方案 | 建议 |
|---|---|
| 完整支持 Chrome/Edge 扩展 | **不要做**。Electron 官方定性为非目标，投入产出比极差 |
| 路径 A（`loadExtension`） | **先验证再决定**。若验证 1 通过且目标扩展确实简单，可作为一个"高级选项" |
| **路径 B（转换 content_scripts）** | **推荐**。复用现有规则系统，风险低，能覆盖"去广告/改排版"这类主要需求 |

**最务实的推荐**：

1. 先做**验证 1**（内容脚本注入 webview）——这决定路径 A 的生死
2. 若只想覆盖"网页改动类"扩展，**直接走路径 B**，且明确告知用户"只支持内容脚本，依赖扩展 API 的功能不可用"
3. 在文档里明确写出**不支持的功能清单**（右键菜单、工具栏按钮、`declarativeNetRequest` 等），避免用户误期待

**与现有能力的关系**：项目已有油猴导入，路径 B 相当于"把油猴导入从单文件扩展到多文件目录"，是自然延伸而非新体系。

---

## 附：不确定性声明

- `content_scripts` 是否注入 `<webview>` guest 页面，**官方文档未明确**，社区报告不一致——必须实测
- Electron 31 与最新版在这些行为上可能有差异，升级时需重新验证
- 未列出支持的 API 属"临时支持"，可能在任何版本被移除，**不应作为依赖**
